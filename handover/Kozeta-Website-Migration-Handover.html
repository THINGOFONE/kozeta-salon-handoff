4. Portability, safety, and costs

Technical risks to verify

  • AI: main client supports a direct OpenAI key, but a configured integration base URL can still be used; product enrichment references Replit AI configuration. Replace provider configuration consistently, not just the key. Preserve prompts/tools without enabling them.
  • State: sessions/OTPs/caches include process-local state; pending payments and revoked-session persistence use PostgreSQL. Audit every table and local file. Verify restart, logout, and multi-instance behavior.
  • Jobs: cache refresh, OTP cleanup, and pending cleanup can run even while the full portal is off. Ensure old/new hosts do not duplicate jobs or webhooks.
  • Callbacks: inventory all provider URLs; known SMS route is /api/sms/inbound. Prepare destination, verify signatures, and avoid duplicate processing.
  • Security: review broad framing headers, proxy trust, session-secret continuity, authorized client access, and Replit-only development plugins.
  • Time/money: preserve America/Toronto and daylight-saving handling. Never perform live charges, refunds, vouchers, or appointments as casual tests.

Earlier planning notes listed deposit-limit, legacy-review, and activation-recovery work. Current source contains a deposit ceiling and recovery/persistence logic, so task labels may be stale. Reconcile current implementation and tests rather than assuming either completion or absence. Keep disabled payment paths off.

  • Phorest link targets correct salon; deposit settings unchanged.
  • Real OTP delivery for supported login inputs; identify actual delivery channel. Email lookup must not be assumed to mean email OTP delivery.
  • Correct client profile, appointments, purchases, loyalty, session restoration, and logout.
  • Disabled AI/payment/refund routes blocked server-side; admin authorization intact.
  • Business email send/receive and transactional email verified separately.
  • Root/www, HTTPS, redirects, canonical URLs, sitemap, and SEO metadata.
  • Webhooks/jobs execute once; backup restoration and monitoring verified.

Cutover and rollback sequence

  1. Obtain architecture, quote, scope, and recurring-cost approval. Coordinate with any existing domain-launch work; never run competing cutovers.
  2. Record current live appearance, source, data, DNS, and provider settings. Define rollback triggers and a responsible contact.
  3. Prepare staging and pass acceptance tests without touching production.
  4. Obtain separate go-live approval; change only agreed web DNS/callback settings while preserving email.
  5. Monitor propagation, SSL, login, booking, email, errors, callbacks, and usage.
  6. If critical checks fail, restore recorded DNS/callback settings and reconcile data changes. DNS reversal may not be immediate.
  7. Retire old services only after a stable observation period and explicit owner approval. Retain backups and review billing separately.
